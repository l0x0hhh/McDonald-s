# A/B/C 开工任务书

> 适用：三人从当前 main 并行开发；A 是刘总。
> 产品目标：[V0.5 方案](../麦门AI点餐助手-项目初步方案.md)。
> 已有接口：[当前契约](./接口与模块契约.md)；新字段：[扩展草案](./接口扩展草案.md)。
> 本文件是分工，不是完成记录，也不是 WorkBuddy 对话记录。

## 一、现在就做这三件事

| 人员 | 第一项交付 | 从哪里开始 | 不依赖谁 |
|---|---|---|---|
| A：刘总 | 公布扩展字段，先接部分需求、无饮料与套餐结构 | 当前 schemas、services、providers 和扩展草案 | 不必等 B 算法和 C 页面完成 |
| B | 接现有三参数 generate_plans，先输出一套正式可解释方案；再接 LLM | backend/schemas.py、sample_planner.py 与现有契约 | 不必等新接口和真实报价；先用 A 提供的菜单输入 |
| C | 用已有 fixture 做选店→需求→方案→模拟结算的完整页面 | docs/api-examples/，现有 HTTP 契约 | 不必等 B 或所有新字段；先显式使用本地样例模式 |

**先交最小闭环，再加差异化。** 每项交付说明“已支持什么、未支持什么、下一项需要谁给什么”，不以“文件建好了”当完成。

## 三、A 的任务：数据事实与集成

### A1：先发布公共能力，第一阶段优先

1. 以扩展草案为目标增加需求字段：不带饮料、会员状态；现有 appetite 和 preferred_tags 保持名称兼容。
2. 补部分需求草稿：目前 ChatIn.current 是完整 Requirements，人数/预算缺一时不能可靠跨轮保留；A 提供 draft，B 合并，C 回传。
3. 读取已核实的套餐规格与选配结构，提供“饮品是否必选、实际组成、份数、规格差价”。未知保持未知。
4. 先保留原有函数签名与 HTTP 字段；只有新字段被请求、解析、决策全链路支持时，才在 config 标记能力可用。
5. 发布对应 JSON 示例，并标明实际接口样例或人工 mock。新字段未接通前，告诉 B/C 不要把它当现有 API。

### A2：把会影响演示的集成问题先处理

- 门店缓存需按模式、城市、关键词区分，不能第二次搜索仍返回第一次结果。
- 获取菜单后保存已取得的结果，避免为了快照再次拉菜单、额外拉默认城市而拖慢请求；快照失败不能覆盖成功的在线响应。
- 营养属于可选信息，失败时保留点餐主流程并标明营养不可用。
- 金额解析失败不能默认免费；会员、随单购与早餐卡资格文字需对应实际类型，不统一写“必须买麦金卡”。
- 服务层校验 B 返回值：价格、数量、餐份、总额和硬约束不满足的方案不能保存/结算；引用应来自对应门店菜单与有效规格。
- 现有规则/样例不能处理的新硬约束要明确拒绝，不能静默忽略。需求变化、换店、上游错误时处理旧方案。
- 当前方案失效与缓存是进程级实现，不宣称已支持多用户隔离；多人同时试用前补会话隔离或明确演示范围。

这些是待修清单，不代表本次已经修改代码。

### A3：报价、会员与活动事实

- 先核实工具列表和返回，不照报告里的建议工具名直接编接口。
- 优先套餐详情、calculate-price 及会员卡费/有效期/资格；读取可用优惠时注明账号要求。
- 向 B 提供原始规则和标准化事实，B 计算开卡比较；A 不再写第二份回本算法。
- 无报价工具时可保留参考价格模式；不能标“已由官方收银核验”。
- 活动工具可用后提供只读活动数据；抽奖、领券和创建订单不作为本轮默认读取动作。
- 模拟结算继续沿用现有 orders，不为演示自动产生真实订单或扣款。

## 四、B 的任务：AI 与省钱 Skill

### B1：立即按现有接口交付

固定入口：backend/llm.py 的异步 extract_requirements(message, current)，backend/skill/__init__.py 的 generate_plans(items, requirements, nutrition)。

- 不另建服务，不直接调用 MCP，不改 A 的路由和公共模型。
- 输入由 A 注入；先支持人数、预算、不辣人数，输出已有 PlanOut 和无解原因。
- 金额用整数分；单品、套餐、多人餐数量要对应实际餐份，不把小食或饮品算成主食。
- 最省只针对已枚举、资格有效的候选；无解不编低价，方案少就少返回。
- 第一阶段没有会员规则时排除资格不明的低价；无需等待开卡接口才交第一版。
- PlanOut 现有必填字段都要填；summary 不留空白占位；plan_id 可设空字符串交 A 保存时赋值。
- B 模块在进程内只探测一次；首次新增模块或改入口后提醒 A 重启后端再接入。

### B2：把四条差异化做实

- 不带饮料：A 发布字段与结构后，明确排除所有饮品及饮品必选套餐，规格未知不伪装满足。
- 饭量：写明轻/正常/大饭量模板，并让主食/小食数量实际变化；预算不足时解释无解。
- 口味：自有规则区分牛肉、鸡肉、鱼、炸物等；不要用“上新/麦金卡”营销标签作口味。
- 开卡：用 A 的同篮子报价、资格与卡费比较，不开卡/已有卡/新开卡分开；缺数返回 unavailable。
- 三种卡片共享硬约束；balanced 先解释为“搭配多样”，有完整证据后才能谈营养均衡。
- 需求提取保留原有状态，处理否定与更正；不辣人数超过总人数时追问，不偷偷截断成总人数。

### B3：增强项

营养按最终单品与份量汇总，缺数标未知；第三方资料与官方来源分开。习惯分析用用户自报频次，不依赖历史订单；固定假设和权益周期完整才估算回本。活动/新品用 A 给的真实数据做口味匹配。

## 五、C 的任务：能展示、能操作的界面

### C1：立即使用已有样例开发

技术按 Vite + React + TypeScript，样式工具由 C 选择。页面兼顾桌面展示与手机宽度。

1. 门店区：城市+关键词搜索与列表选择，显示地址/营业状态/来源；不画虚假的定位地图。
2. 聊天区：快捷示例、输入框、追问和可编辑的结构化需求摘要；预算标清总额/人均。
3. 方案区：最省/搭配多样/口味匹配，展示金额、数量、适合人数、预算余额、理由和数据依据。
4. 确认区：已选方案明细与模拟结算，清楚标“演示，不会扣款”。
5. 状态：加载、空结果、无解、失败、降级、过期、图片失败；源数据与算法样例标记分别展示。

已有 fixture 是带 code/data/msg 的完整响应，按 data 读取；请求 plans 时只提交 store_code 和完整 requirements，不把整个 fixture 回传。

A 发布草稿能力前，C 在本地保留已填信息；缺人数/预算时不要把残缺对象塞入 current。可以用完整表单补齐，或把已确认信息汇总进下一次 message。

### C2：预留并逐步接新能力

- 不带饮料开关、轻/正常/大饭量、偏好标签放在需求摘要旁，方便展示“改一个条件→方案变化”。
- 会员对比是选中方案的可选面板；习惯频次只在用户展开时收集。
- 营养默认折叠，不把热量当唯一目标；显示覆盖率、缺项和第三方来源。
- 活动/新品为轻量发现区域；无数据时不制造假活动卡片。
- 通过集中 API 适配和 config 能力标记接字段；**能力未发布时不向旧接口发送新硬约束**。
- 可以用人工 mock 做布局，但页面必须可辨认，切到真实后端时移除 mock 成功假象。
- 用户修改需求或门店后立即清掉旧方案与结算选择；不依赖旧 plan_id 碰巧还能用。

## 六、怎么交接与合并

1. B/C 从拿到本次文档的最新 main 新建功能分支，先看现有代码，不重新生成公共骨架。
2. 第一批：B 的现有接口 Skill + C 的现有接口页面可独立提交，A 逐个合并。
3. 第二批：A 先合公共模型、能力标记与样例，再通知 B/C 接增量；双方拉取对应提交。
4. 第三批：接不带饮料/饭量/口味；报价/会员有事实再接比较；营养和活动按剩余时间加。
5. 交付附清单：本次文件、输入输出变化、已支持场景、未实现项、未运行验证说明和所需依赖。
6. 时间与共同场景见项目方案。规则：不超预算、不漏硬约束、不编数据、不隐藏演示状态。
