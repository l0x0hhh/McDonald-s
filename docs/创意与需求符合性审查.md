## 二、重点问题逐条说明

### 2.1 遗漏①：「不喝饮料」——最该补的一条

DAWN 原话：*「还有怎么选才能不喝饮料[破涕为笑]」*，这是她自己举的第一个具体痛点。

现状：`Requirements` 没有排除饮料的字段，`sample_planner` 只用套餐，而套餐默认带饮料（如「大堡口福三件套」默认可乐中杯）。

**技术硬约束**：实测 `query-meal-detail` 的「选择套餐内饮料」轮次 `minQuantity=1`，**套餐内不能完全去掉饮料**，只能换成牛奶/红茶/咖啡等。所以「不喝饮料」只能靠两种绕行：
- 方案 A：改用**单品组合**（主堡 + 小食），完全不进饮料轮次；
- 方案 B：套餐内把饮料换成最便宜/可带走的（如锡兰红茶 10.5 元），并在明细里标「饮料可换，不影响主餐」。

建议：`Requirements` 增加 `exclude_beverage: bool`，chat 识别「不喝饮料/不要饮料/自带水」，plan 层按方案 A 优先、B 兜底，并在 `reasons` 里写明「套餐含饮料无法完全去掉，已换成 X / 已改用单品组合」。这条做出来就是竞品没有的差异化点。

### 2.2 偏差②：「考虑饭量」——字段是摆设

余清涂原话：*「就是告诉他之前学长说的人数预算忌口哪些，还可以考虑一下饭量」*。

现状：`schemas.py` 有 `appetite: light|normal|heavy`，`chat_service` 也能从「胃口大/吃得少」解析出来，但 **`sample_planner` 里一次都没读这个字段**（已 grep 确认）。属于「表面齐活、实际空转」。

建议：让 appetite 真正影响份数——`light` 用两件套或单品组合、`normal` 用三件套、`heavy` 额外配小食；并在 `reasons` 里写出「按饭量 normal 配 1 主食 1 小食 1 饮料」。B 接正式算法时必须落实，否则评审一问就露。

### 2.3 偏差③：「按口味推荐」——数据源用错了

DAWN 原话：*「活动和新品推荐感觉也比较有意思，这个可以按照口味推荐」*。

现状：`preferred_tags` + taste 方案存在，但口味标签取自 MCP 的 `tags`。实测这些 tags 是 **`全球爆款`、`限时特惠`、`麦金卡`、`上新`、`人气`** 这类营销标签，**没有一个口味维度**。所以「口味匹配方案」现在是在拿营销标签做匹配，属于空转。

建议：仿照已有的 `spicy_rules.json`，建一份 `taste_rules.json`（牛肉/鸡肉/鱼/板烧/炸物/咖啡/甜品/无糖），从商品名推断口味标签；taste 方案改用这张表，MCP tags 只用于「新品/限时」角标。改动量小，效果立竿见影。

### 2.4 遗漏④：开卡对比——数据现成却没做

树雾晚鲸原话：*「你开卡之后，这个餐饮之后根据你的购买习惯是否划算，就是对比两种方案」*。

现状：方案列 P1；代码里我反而**主动排除了所有需麦金卡的商品**（因为低价不买卡会按原价结算）。

**但这里恰恰是现成素材**：快照里有 **18 个商品**标着「随单购麦金卡优惠」，低价与原价差额极大——全明星双人分享餐 49.9 vs 117、人气超值四件套随心选 28 vs 57、BFF 四宫格双人餐 62.9 vs 123。这批数据足够做一个「开卡 vs 不开卡」的真实对比，而且**是别队想不到的深度**。

建议：把开卡对比从 P1 提到 P0 边缘，最小实现——同一份需求生成两版：不开卡版（当前实现）与开卡版（含卡费 + 低价商品），输出「本单省 X 元，卡费 Y 元，本单净收益 Z 元」。方案文档 §6.2 已写清「分别列出未开卡价格、会员价格、开卡费用和本次净收益」，口径现成，只差实现。

### 2.5 遗漏⑤：活动与赠品——MCP 有能力，却被排到赛后

DAWN 连发三条：*「这个活动是我们能够自己设计的吗」「完成一个游戏或者是活动，能给我送点想吃的东西」「比如说像可乐这种东西，我就根本不想花钱买，但是如果我参加点活动他能送，那我一定会玩」*。这是她**最强的情绪点**。

现状：方案第十节把它归为「游戏化，本次不作为交付依赖」。

**关键发现**：麦当劳 MCP 实际提供 `campaign-calendar`（活动日历）、`query-promotions`（促销）、`draw-lottery`（抽奖）、`query-lottery-info`、`query-my-prizes` 五个活动类工具。也就是说「今日有什么活动、参与能拿什么」**不需要自己设计活动，官方已有**。

建议：把「活动推荐」从后续提到 P1，最小版只做 `campaign-calendar` + `query-promotions` 的展示，告诉用户「今天有 X 活动，凑单到 Y 可得 Z」。抽奖类工具需账号态，先核实可用性再决定。这比凭空设计游戏化规则更真实，也更符合「用真实 MCP」的评分点。

### 2.6 冲突⑥：支付链接 vs 模拟结算

余清涂原设想：*「最后给出一些方案，用户选一个，ai 再生成支付链接」*。
方案 V0.4 写的是：*「团队已确认：模拟支付演示」*，代码实现为 `status=simulated`、`is_demo=true`。

判定：这是**团队后续决策覆盖了原始设想**，属于有意降级，不算错误。但两点必须注意：
1. MCP 实际有 `create-order`、`calculate-price`、`mall-create-order`，**真实下单能力存在**；如果现场评委要求"真的能点"，需要有话说。
2. 路演和 README 必须主动说明「模拟结算为有意设计，避免产生真实扣款」，否则会被当成没做完。当前 README 已写，但方案里那句「团队已确认」需要保留并强调。

建议：不改实现，但补一条「若需真实下单，接入点已留好（`/orders` 换 `create-order`）」，作为答辩预案。

### 2.7 冲突⑦：膳食纤维——创新点没有数据源

焦凤梨酥原话：*「各大营养元素（比如碳水脂肪蛋白质膳食纤维）这块大概可以算是一个创新点」「本餐膳食纤维比例偏低，就可以建议加购苹果片」*。

**实测结论**：`list-nutrition-foods` 返回 160 条，字段只有 `energyKj / energyKcal / protein / fat / carbohydrate / sodium / calcium`，**没有膳食纤维**（已 grep 验证）。她要的「膳食纤维均衡建议」在官方数据上做不出来。

同时 DAWN 明确说过 *「都来吃麦当劳了，热量应该也不怎么考虑吧」*，团队内部对营养这条本身有分歧。

建议：
- 指标换成**有数据的**：蛋白质、脂肪、碳水、钠（钠最有故事——一份双层安格斯钠 1373mg，可以做「钠偏高，建议换无糖可乐」）。
- 若坚持膳食纤维，必须注明数据来自第三方测评（xhs），存在准确性与合规风险，且不能与官方数据混排。**不建议在 25 小时内做**。
- 营养优先级：方案 §2 定为 P1 是对的，但要先把「营养数据匹配率」修好——当前套餐名对不上单品名，`matched` 基本全 False，等于营养模块现在完全没输出。

### 2.8 部分符合：定位与扫码

余清涂：*「可以让人自己填或者我们也搞个定位功能」「如果能整出 app 的话可以加个扫码识别门店」*。

现状：`GET /stores` 支持 `city` + `keyword` 参数，前端可让用户自己填，这部分**符合**。但：
- **实测门店经纬度返回 `0.0`**（5 家店全是），地图打点、距离计算、"附近门店"做不到，定位功能只剩「按城市+关键词搜」。
- 扫码识别门店需要门店二维码体系，MCP 无对应能力，**不建议做**。

建议：对外表述改为「按城市与位置关键词选店」，不要承诺定位与地图；扫码明确列为不做。

## 三、必须现在拍板的三个分歧

1. **营养做不做、做到什么程度？** DAWN 说不用管热量，焦凤梨酥当创新点。25 小时内只能二选一：要么用「钠/蛋白质」做一个有数据的简版，要么直接砍掉、把时间给「不喝饮料」和「开卡对比」。
2. **活动模块要不要加？** MCP 有工具，但没实测过；`campaign-calendar` 若能用，是低成本亮点。
3. **模拟结算是否对外明确说明？** 建议明确说明并准备答辩口径。
