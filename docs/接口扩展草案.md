# 接口扩展草案 · V1.1

> 状态：**待 A 实现，不能当作现有 API**。
> 现有接口以 [当前契约](./接口与模块契约.md) 与 backend/schemas.py 为准。
> 维护：A；B 提供决策模块；C 在能力发布后接入。
> 本轮仅编写文档，不新增接口、模型、依赖或 JSON 实测样例。

## 一、先不阻塞开工

- 现有 HTTP 路径、code/data/msg 响应包装、整数分金额以及三个函数参数继续使用。
- 第一批 B/C 按旧接口开发；新字段不能导入尚不存在的模型，也不能发给旧接口后误以为已生效。
- 新功能先由 A 合模型/编排与示例，再由 B/C 接入。能力标记必须反映全链路，而不是仅“字段存在”。
- 现有 Pydantic 模型没有为新需求约定严格的额外字段拒绝；未知字段可能被忽略。A 应明确拒绝未支持的硬约束，C 不能靠请求成功判断功能可用。
- 下列字段名是团队目标；A 如需调整，在同一 PR 更新本文与 fixture，再让 B/C 跟进，不留两个版本。

## 二、config 能力标记（计划）

现有 GET /api/v1/config 返回内容保留，拟增加：

~~~json
{
  "contract_version": "1.1",
  "capabilities": {
    "chat_draft": false,
    "exclude_beverage": false,
    "appetite_planning": false,
    "taste_matching": false,
    "membership_comparison": false,
    "habit_estimate": false,
    "nutrition_summary": false,
    "campaigns": false
  }
}
~~~

这是人工设计示例，不是接口实测结果。现有服务没有这些字段，C 应将缺失理解为扩展未发布。某个能力只有 A 的输入/数据与 B 的决策、服务层校验均可用才设 true；上游数据临时不足由响应里的状态继续说明。真实支付不在本版能力范围。

若收到已明确但不可执行的新硬约束，拟返回 HTTP 409、E_CAPABILITY_UNAVAILABLE，并解释缺的能力；不能自动退回含饮料的普通方案。原有错误码保持。

## 三、需求字段

现有 Requirements 的 people、budget_type、budget_fen、dietary_constraints、appetite、preferred_tags 保持名称。拟新增：

| 字段 | 类型 / 默认 | 语义 |
|---|---|---|
| exclude_beverage | bool，默认 false | true 代表整单不含饮品，包括茶、牛奶、咖啡等；false 代表未限制，不是必须配饮品 |
| membership_status | unknown / none / active，默认 unknown | 用户自报的当前状态；不能替代账号资格核验，也不自动购卡 |
| meal_frequency_per_month | 非负整数或 null，默认 null | 用户自报次数，0 与未提供分开 |
| habit_horizon_months | 正整数或 null，默认 null | 用户想分析的月数；必须结合实际卡有效期 |
| habitual_tags | 字符串数组，默认空 | 常买品类，与本餐 preferred_tags 分开；不等于真实订单历史 |

preferred_tags 第一批约定为 beef、chicken、fish、fried、grilled、sweet、sugar_free；B 负责可解释匹配，未映射或有歧义的偏好要提示。营销属性仍保留在 MenuItemOut.tags，不把它们当口味字段。无需为了保存口味再建第二套菜单。

dietary_constraints 当前仍只承诺 non_spicy。后续如扩其他忌口，需同步模型、来源和判定规则；不能只给 UI 增加按钮。

### 3.1 部分需求与多轮对话

拟新增 RequirementsDraft：允许 people、budget_type、budget_fen 等未收集字段为 null，并保留已明确的饮料、饭量、口味、不辣人数等信息。

- ChatIn.current 改为可接收 RequirementsDraft，兼容已完整的原 Requirements 对象。
- ChatOut 增加 draft，保存本轮合并后的部分信息；requirements 只在必填项齐全且校验通过时返回完整对象，否则为 null。
- C 下一轮优先回传 draft；只有 ready=true 且 requirements 非空时才能请求 plans。
- B 的 extract_requirements 返回 draft、requirements、missing_fields、follow_up、parse_source、notes。A 编排保留实际解析来源。
- 不辣人数未知时追问；大于总人数时要求修正，不能用 min 静默收敛。
- 预算口径矛盾时确认；用户修改“不是 6 人，是 4 人”时更新已有字段，其他已明确约束保留。
- 旧 B 模块不返回 draft 时 A 兼容完整 requirements；不能假装已经支持跨轮部分状态。

人工设计的单轮示例，仅表达目标结构：

  "ready": false,

~~~

## 四、A 向 B 提供的餐品事实

现有 MenuItemOut 字段保留，拟补 food_role（main/side/beverage/combo/unknown）和 beverage_status（none/contains/unknown）。none 仅用于已证实不含饮品的单品或组合；不能因为名称没写“可乐”就填 none。

套餐选配明细放在计划中的 PlanningContext.combo_details 中，按菜单商品 code 索引，至少包括：

| 内容 | 必须解释清楚的含义 |
|---|---|
| rounds | 每轮选择的最小/最大数量、选项、默认项 |
| option code / name | 可回传报价的真实标识、选项名称 |
| diff_price_fen | 选项差价，单位分；解析失败记未知，不记零 |
| food_role / beverage_status | 用于主食份数、无饮料与饭量判定 |
| servings / quantity | 一份组合实际包含什么与数量，是否为已核实值 |
| source / fetched_at | 数据来源、采集时间；未知选配或缺详情单独说明 |

B 输出方案时保持原 spec 字符串作为展示摘要，拟另加 selected_options 保存结构化选配（round 标识、option code、数量）。A 校验后用于报价；不能只凭中文 spec 重新猜商品。

不带饮料时，缺套餐组成或饮品轮次强制选择的组合不参与。单品也需可靠分类，未知项不能被用来伪装满足约束。餐份未知的多人餐不能只凭名称放大主食数。

~~~python
# 第二阶段目标：新增可选关键字参数，旧三参数调用仍有效。
def generate_plans(items, requirements, nutrition, *, context=None):
    ...
~~~

context 拟由 A 定义为 PlanningContext，含 store_code、combo_details、membership_facts 和数据来源/时间。B 不直接向上游请求。A 在调用前检查函数签名决定是否提供 context；不要因业务函数内部 TypeError 再调用一次。

旧 Skill 不支持新硬约束时，A 返回能力不可用；不能将“忽略新字段后算出来的旧方案”视为成功。

实际顺序：

1. A 拉取门店菜单、可用套餐明细和会员事实；B 用这些数据生成候选和明确的规格。
2. A 在支持时对候选调用真实算价，记录资格、卡费是否已含与报价时间；不支持时保留参考估算标记。
3. A 按报价更新总额与明细，重新检查预算和排序，超预算或规格无效的移除；必要时请求 B 补候选，不混用旧总价。
4. 对需要开卡比较的同篮子，A 分别拿到资格有效的场景报价，交 B 的独立纯函数 compare_membership 处理；函数细节在双方对应实现 PR 冻结。
5. A 校验最终结果，保存方案并返回 C。在线菜单与在线报价分开标记，不能只看 live_mcp 就当最终价格已核验。

PlanningContext 目前不存在；这部分是目标设计，不是当前可直接复制运行的模块。

## 六、开卡结果与习惯分析（计划）

PlanOut 拟新增可选 membership_comparison，未接入时为 null；接入后最小结构：

| 字段 | 约定 |
|---|---|
| status | available / unavailable |
| reason | 缺数据或不适用原因；available 时可为空 |
| same_basket | 是否同商品、同数量、同规格、可比资格 |
| without_card_fen | 真实可取得的不开卡应付；不可取得则 null，不默认用原价 |
| existing_card_food_fen | 已有卡场景餐费；须注明资格假设 |
| new_card_total_fen | 本次新开卡总成本，卡费只能计入一次 |
| card_fee_fen | 真实新增卡费；缺数据则 null |
| net_saving_fen | 同篮子不开卡应付减新开卡总成本；亏钱保留负值 |
| price_basis | menu_estimate / live_quote / demo_snapshot |
| source / fetched_at / assumptions | 来源、时间与资格/时段/限购等假设 |
| habit_estimate | 未实现或信息不全为 null；有值也必须给条件和覆盖周期 |

规则由 B 计算，A 提供事实。核心缺项时 status=unavailable，所有无法证明的数值为 null，不能填 0。引用实际会员状态需按账号核验；用户自报 active 仅作为比较场景，不能让其绕过价格资格。

习惯分析：同样的合格篮子每次可节省 s 分、一次卡费 f 分，且有效期、次数上限、互斥条件完整覆盖时，s>0 才可用 ceil(f/s) 表达“累计节省达到卡费”的次数。s<=0 不回本；f=0 则无需额外回本。周期内购买次数不足时如实展示；频次/常买品类不等于精确历史，不对未来价格作保证。

如果两种方案不是同一篮子，可展示内容和总价差异，但 same_basket=false，net_saving_fen 为 null，不给纯会员节省或回本结论。

## 七、营养结果（计划）

保留现有单项 NutritionOut，拟补 fiber_g、数据时间和字段级来源；fiber_g 默认 null，不能臆造。PlanOut 拟新增可选 nutrition_summary：

- totals：只对已匹配且单位一致的实际单品按数量汇总；各指标允许 null。
- coverage：按实际单品份数和具体指标说明覆盖情况，不按金额加权冒充营养完整度。
- missing_items / missing_metrics：无法拆解的套餐、未匹配单品与缺失指标。
- sources：官方 MCP/第三方资料分别列出来源、规格、日期与是否估算。
- suggestions：有依据、满足预算和忌口的可选替换；数据不足不下定量结论。

有部分数据时标“已知部分合计”，完整时才能称整单合计。第三方纤维资料不改变其他字段的官方来源，也不能凭纤维未知就断言本餐纤维低。C 默认折叠面板，不强制健康排序。

## 八、活动与新品（计划）

A 核实后可新增 GET /api/v1/campaigns?store_code=...，保留 code/data/msg 包装；当前尚无该接口。

data 最小字段：items、data_source、fetched_at、degraded_reason。每项包含 id、title、开始/结束时间（无数据为 null）、适用门店/时段、账号或会员条件、奖励描述、来源入口、可用标签；不承诺必得奖励。

- MCP 原营销 tags 可辅助发现新品，但口味排序由 B 的规则完成。
- 活动接口失败不阻塞主点餐流程；C 显示暂不可用或隐藏。
- 不自动调用抽奖、领券、下单等写操作；先交只读发现与推荐。
- 未得到实际工具与响应证据前，不把具体活动工具名或赠品写成已支持。
