## 二、统一约定

| 项 | 约定 |
|---|---|
| 金额 | 一律整数「分」。前端只做显示格式化，不重算业务价格 |
| 成功响应 | `{"code": 0, "data": ..., "msg": "ok"}` |
| 失败响应 | 对应 HTTP 状态码 + `{"code": "E_XXX", "msg": "...", "data": null}` |
| 数据来源 | `data_source`: `live_mcp`（真实 MCP）/ `demo_snapshot`（演示快照） |
| 降级 | `degraded_reason` 非空表示已从真实 MCP 降级到快照，页面必须提示 |
| 模拟结算 | 订单固定 `status=simulated`、`is_demo=true` |
| 方案有效期 | 30 分钟；当前代码在新门店生成出方案后清理其他门店方案，未做到选店即失效；C 换店或修改需求时应立即丢弃旧方案 |

### 稳定错误码

| 错误码 | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `E_PARAM` | 422 | 参数有误 | 展示字段错误 |
| `E_UPSTREAM` | 502 | MCP 不可用 | 提示切换演示模式 |
| `E_UPSTREAM_TIMEOUT` | 504 | MCP 超时 | 同上，可重试 |
| `E_PLAN_NOT_FOUND` | 404 | 方案不存在/换店后失效 | 回方案页重新生成 |
| `E_PLAN_EXPIRED` | 409 | 方案超 30 分钟 | 回方案页重新生成 |
| 🆕 `E_CAPABILITY_UNAVAILABLE` | 409 | 收到了已明确但当前全链路不支持的硬约束 | **按硬约束拒绝处理**：提示该约束暂不可满足，让用户取消约束或换门店。**绝不能**把它当成普通失败后继续展示含饮料的方案 |
| `E_INTERNAL` | 500 | 内部错误 | 通用错误提示 |

已完整的原 `Requirements` 对象仍然兼容，可直接继续回传。

```json
    "exclude_beverage": false,
    "membership_status": "unknown",
    "meal_frequency_per_month": null,

  "follow_up": null,
  "ready": true,

  "notes": []

```

🆕 多轮与矛盾处理（已实装，实测口径）：

| 场景 | 行为 |
|---|---|
| 先说人数、后说预算 | 已收集字段保留，只补新值 |
| 「其中 2 个人不吃辣」 | 忌口句式里的数字**不会**被当成总人数（`people` 保持 6） |
| 「不是 6 个人，是 4 个人」 | 取更正后的值，预算等其他字段保留 |
| 不吃辣人数 > 总人数 | `requirements=null`、`ready=false`、`follow_up` 要求更正，**不静默取 min** |
| 只说「有人不吃辣」没给人数 | `missing_fields` 含 `non_spicy_people` 并追问 |

**`ready=false` 时不要调 `/plans`。** 只有 `ready=true` 且 `requirements` 非空才提交。

- `ready=false` 时展示 `follow_up` 继续追问，**未齐时不要调 `/plans`**。
- `parse_source`：`rule`（内置规则兜底）/ `llm`（B 接入后）/ `demo_template`。
- 未给忌口人数时会追问 `有几位不吃辣？`，不会擅自按全部不辣处理。
- 金额只说数字没说口径时默认按总预算，并在 `notes` 里说明。
- 当前 `appetite` 只是被解析/保存，演示组合不会据此改变饭量；`preferred_tags` 也未由规则解析主动提取。不能把字段存在等同于决策已生效。

要点：

- **无解时 `plans=[]` 且 `unsatisfiable_reason` 非空**（HTTP 仍 200），页面展示原因与建议，不要硬凑三张卡片。
- `type` 取值：`cheapest` / `balanced` / `taste`。三种口径撞出同一组合时只返回一套并说明。当前 `balanced` 仅控制商品多样性，C 展示为“搭配多样”，不宣称营养均衡。
- `spicy_level`：`mild`（本地规则判定不辣）/ `spicy` / `unknown`（**未知，不得当成不辣展示**）。
- 当前 mapper 会将含「随单购」「麦金卡」「早餐卡」的类型标 `requires_membership=true`；资格与具体卡种仍需 A 核实。样例排除这些商品，**不能直接按低价求和，也不能当成已实现开卡对比**。
- `suggestions` 里出现 `demo_sample` 说明当前走的是 A 的演示样例而非 B 的正式算法，**路演时不能说成算法已接入**。
- `plan_id` 由服务端保存并绑定门店与需求，结算按服务端方案重建金额。
- 🆕 `capabilities` 是**本次请求**实际可用的能力；字段存在不等于功能可用，C 以它为准。
- 🆕 价格仍以菜单参考价为准（`calculate-price` 已实测可用但尚未接入业务链路）；`live_mcp` 仅表示菜单来源，不表示价格已通过收银算价。

#### 🆕 3.3.1 不带饮料（硬约束）

`requirements.exclude_beverage=true` 表示整单不含饮品（含茶、牛奶、咖啡）。

- **这是硬约束，不是偏好**。决策未支持或缺少必要事实时返回 **HTTP 409 `E_CAPABILITY_UNAVAILABLE`**；
  有能力但没找到符合预算等条件的组合时，返回 `plans=[]` 与原因。两种情况都不能展示含饮料方案。
- 轮次名称不能证明不含饮料。快照中的「人气经典随心配」「精选超值随心配」轮次叫蓝区/粉区，
  默认选项仍有可乐或怡泉；「学生专享」还存在未核验的身份资格。
- **A 的无饮料演示样例只使用已确认的主食单品**。B 可搜索套餐内的无饮料替换方案，
  但须提交全部选配，并通过轮次数量、选项差价、实际饮料与餐份校验。
- 方案 `checks` 里会有独立的「不含饮料」校验项，可直接在页面上展示。
- 样例未搜索所有套餐替换，不保证全局最省；不要继续使用旧误判产生的价格对比作为演示结论。

#### 🆕 3.3.2 方案保存前的服务端校验

B 或样例返回的方案在保存前会被逐项核对，不通过的直接丢弃并在 `suggestions` 写明原因：

- 商品来自该门店菜单；周边和未核验会员/身份资格商品不能计入。
- 现价未知、解析失败或为负时，商品从可规划菜单排除；真实 `0` 元保留。
  原价缺失或低于现价时，按现价作原价参考并在 `role_evidence` 说明，不虚构优惠。
- `selected_options=[]` 表示使用可明确还原的默认选配。非空列表必须包含**完整选配**，
  每项 `quantity` 是**每份套餐内部数量**；不能只传修改的那一轮。缺失或模糊的默认结构会被拒绝。
- 校验轮次、选项、重复项、正整数数量、每轮上下限、每个选项上限；
  未知差价不能当零；传入差价必须与事实一致。`support_modify` 保留上游原值，
  本版未核实其与套餐换配的关系，不用该字段推断轮次的可选范围；可选范围以 `rounds/options` 为准。
- 菜单现价/原价加上实际选配差价后得到单价，再乘套餐购买数量。
  此处仍是菜单参考价，不是 `calculate-price` 的实时收银报价。
- 主食才增加餐份，小食和饮料记 `0`；套餐按实际所选主食数量统计。
  混合套餐只有所选食物全部可确认不辣时，才把该套餐餐份计入不辣人数，避免高估。
  校验会核对每行 `servings`/`spicy_level`，以及总额、原价、优惠、预算、余额和餐份汇总。
- B 可复用 `backend.services.meal_facts.resolve_meal_facts()` 获取当前核实口径；
  它返回 `(MealFacts | None, 问题列表)`，不做组合搜索或优惠决策。

要点：`diff_price_fen` 单位是**分**，解析不出来时是 `null`（不是 0，0 表示确认不加价）；

## 四、A ↔ B 的模块契约（关键）

A 不实现 B 的组合搜索，负责取数、适配、调用与独立事实校验。本次合并范围见 [A/B 整合说明](./A-B整合说明.md)。

### 4.1 需求提取：`backend/llm.py`（B 维护）

🆕 `current` 现在是 **`RequirementsDraft | None`**（所有字段可缺省），不再是完整 `Requirements`。

```python
from backend.schemas import Requirements, RequirementsDraft

async def extract_requirements(
    message: str,
    current: RequirementsDraft | None,   # 上一轮合并后的草稿，可能是缺字段的
    *, demo_mode: bool = False,
) -> dict:
    merged = (current or RequirementsDraft()).merge(RequirementsDraft(people=6))
    return {
        "draft": merged,                     # 🆕 本轮合并后的草稿（推荐返回）
        "requirements": merged.to_requirements() if merged.is_complete() else None,
        "missing_fields": merged.missing_fields(),
        "follow_up": None,
        "parse_source": "llm",
        "notes": [],
    }
```

- 🆕 返回 `draft` 后，C 下一轮回传它即可跨轮保留；**不返回也没关系**，
  A 会用 `requirements` 反推草稿（但那样可能丢掉尚未收集进完整需求的字段）。
- 🆕 `RequirementsDraft` 自带 `merge()` / `missing_fields()` / `contradictions()` /
  `is_complete()` / `to_requirements()`，B 直接用即可，不用自己写合并逻辑。
- 🆕 **矛盾必须上报**：不吃辣人数超过总人数时，让 `contradictions()` 非空或自己写进
  `follow_up`；A 无论如何都会再检查一遍并强制追问，不会静默取 min。
- A 侧兜底仍保留：`ready` 只在 `requirements` 非空且无缺失、无矛盾时为 true。
- `DATA_MODE=demo` 使用 B 的规则并标 `demo_template`；在线模型异常时使用相同规则并标 `rule`，在 `notes` 明示。
- 金额已知但总额/人均未确认时继续追问；草稿回传 `pending_fields`、`notes`。显式空列表可清除忌口/偏好，未提及的字段保持原值。
- 草稿保留矛盾并追问，完整 `Requirements` 拒绝不辣人数超限，不再截断人数。
- **禁止在该模块里直接调 MCP**——业务数据由 A 的 providers 统一供给。

### 4.2 方案生成：`backend/skill/__init__.py`（B 维护）

```python
from backend.schemas import MenuItemOut, NutritionOut, PlanOut, Requirements, PlanningContext
```

- 同步或 `async` 均可，A 会自动兼容。
- `PlanOut.plan_id` 目前是必填字符串；B 可传 `plan_id=""`，A 保存时赋值，不能省略必填字段。其余字段以 `backend/schemas.py` 为准。
- 约束必须满足：`total_fen <= requirements.total_budget_fen`、
  `servings_total >= requirements.people`、`non_spicy_servings >= requirements.non_spicy_people`。
- **不要自行读取 MCP 或另建菜单数据**（协作文档约定）。
- 正式模块异常或方案不合法时返回 409 `E_CAPABILITY_UNAVAILABLE`，不换成忽略饭量/口味的样例。
- 仅模块未装载时保留旧样例，并标 `algorithm_source=demo_sample`；该入口拒绝显式饭量变化与口味需求。
- **旧三参数入口仍可用**；新 `context` 已接入但保持可选，不要改成必填第四位置参数。
- `CAPABILITIES` 必须是字典，只有值严格为布尔 `True` 才启用能力；接收 `context` 本身不代表算法支持该功能。
  未声明无饮料能力的 B 模块会在该硬约束请求中被明确拒绝。旧三参数模块也可声明其已实现的单品无饮料能力。
- 饭量与口味可随 B 显式声明启用；开卡、习惯、整餐营养及活动因 A 的事实链路尚未齐备，仍为 false。
- `services/skill_adapter.py` 将 A 的轮次结构转换成 B 的已核实默认选配事实；原菜单不被修改，原价与现价包含相同规格差价。
- 方案 `selected_options` 对外保持 `option_code`，兼容内部输入的 `code`；餐份、小食、饮料和组成需通过 A 的独立重算。
- 响应保留 `capabilities`，增加 `algorithm_source`；方案包含 `price_basis`、`side_servings_total`、`nutrition_summary`。会员事实不足时返回 `membership_comparison.status=unavailable`，未知金额和报价依据为 null。
- `session_scope=single_demo`：聊天输入或重新生成都会撤销旧方案，多用户隔离尚未实现。
- 首次新增 B 模块或修改入口后通知 A 重启后端；当前模块探测结果会缓存，不保证自动重试加载。

### 4.3 参考实现

`backend/services/sample_planner.py` 是一份可运行的简化实现，
B 可以照着它理解数据结构与约束口径，但它是**要被替换的样例，不是正式算法**：
不做优惠叠加、不做营养优化、不使用开卡对比。当前样例只返回最省候选与搭配多样候选，
去重后为 1～2 套，不用营销标签冒充口味匹配。一般方案使用可核实的默认套餐或主食单品；
无饮料方案只用单品。搜索没找到组合不代表正式算法也无解。

## 五、给 C 的前端对接要点

1. **金额只显示不计算**：`total_fen / 100` 格式化即可。
2. **三个标识必须可见**：`data_source`（真实/演示）、`degraded_reason`（降级原因）、订单 `is_demo`。
3. **`unknown` 辣度要透出**：建议文案「辣度未知，请按个人情况选择」，不要默认显示不辣。
4. **状态覆盖**：加载中 / 上游失败 / 无解（`unsatisfiable_reason`）/ 方案过期（409）。
5. **换门店或改需求后**：C 立即清空旧方案与结算选择并重新生成；当前后端清理旧方案有时机限制，不能依赖请求必然返回 `E_PLAN_NOT_FOUND`。
6. `docs/api-examples/` 中已有 JSON 是历史采样；字段以当前模型与本文为准，新回归用例尚未运行，不要把旧响应当成这次修订的验收结果。
7. 以 `/config` 和 `/plans` 的 `capabilities` 判断能力；只对仍不可用的功能采用明确标记的人工 mock。`live_mcp`、`parse_source`、`demo_sample` 和订单 `is_demo` 分别说明数据、解析、算法、结算状态。
