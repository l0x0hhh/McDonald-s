# 前后端接口与模块契约（A → B / C）

> 生成时间：2026-10-24 12:00（北京时间）
> 维护：A（后端与集成）。本文所有示例均来自**真实运行接口的返回**，
> 原始完整 JSON 在 `docs/api-examples/`，可直接当前端 fixture 使用。
> 本文不涉及 B 的算法实现与 C 的页面实现，只约定双方对接面。

## 一、启动后端

```bash
# 仓库根目录
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt   # Windows
# .venv/bin/python -m pip install -r backend/requirements.txt         # macOS/Linux

# 配置凭据：复制 backend/.env.example 为 backend/.env，填入 MCP 地址与 Token
# 无凭据时把 DATA_MODE 改成 demo，即可用本地快照跑通全流程

.venv/Scripts/python.exe -m uvicorn backend.main:app --port 8000 --reload
```

- 接口文档（自动）：`http://127.0.0.1:8000/docs`
- 健康检查：`GET /healthz`
- 本地验证过的环境：Python 3.13 + fastapi 0.162 + httpx 0.28
- 数据目录：`backend/data/`（辣度规则、快照、方案持久化）
- 演示快照刷新：`.venv/Scripts/python.exe -m backend.scripts.build_snapshot --store 1400011`

## 二、统一约定

| 项 | 约定 |
|---|---|
| 金额 | 一律整数「分」。前端只做显示格式化，不重算业务价格 |
| 成功响应 | `{"code": 0, "data": ..., "msg": "ok"}` |
| 失败响应 | 对应 HTTP 状态码 + `{"code": "E_XXX", "msg": "...", "data": null}` |
| 数据来源 | `data_source`: `live_mcp`（真实 MCP）/ `demo_snapshot`（演示快照） |
| 降级 | `degraded_reason` 非空表示已从真实 MCP 降级到快照，页面必须提示 |
| 模拟结算 | 订单固定 `status=simulated`、`is_demo=true` |
| 方案有效期 | 30 分钟；换门店后其他门店的方案全部失效 |

### 稳定错误码

| 错误码 | HTTP | 含义 | 前端处理 |
|---|---|---|---|
| `E_PARAM` | 422 | 参数有误 | 展示字段错误 |
| `E_UPSTREAM` | 502 | MCP 不可用 | 提示切换演示模式 |
| `E_UPSTREAM_TIMEOUT` | 504 | MCP 超时 | 同上，可重试 |
| `E_PLAN_NOT_FOUND` | 404 | 方案不存在/换店后失效 | 回方案页重新生成 |
| `E_PLAN_EXPIRED` | 409 | 方案超 30 分钟 | 回方案页重新生成 |
| `E_INTERNAL` | 500 | 内部错误 | 通用错误提示 |

## 三、HTTP 接口

### 3.1 `GET /api/v1/stores`

查询参数：`city`、`keyword`（可省略，默认 `广州` / `天河区体育西路`）。

返回 `data`：

```json
{
  "stores": [
    {
      "store_code": "1400011",
      "name": "麦当劳广州今日广场餐厅",
      "address": "体育西路77号首层及二层",
      "distance": 82,
      "business_status": true,
      "business_hours": "00:00-23:59",
      "supports_reservation": true
    }
  ],
  "data_source": "live_mcp",
  "fetched_at": "2026-10-24 11:45:53",
  "degraded_reason": null
}
```

注意：MCP 门店经纬度实测返回 `0.0`，**不能用于地图打点**。

### 3.2 `POST /api/v1/chat`

输入：`{"message": "...", "current": Requirements | null}`（current 为上一轮已收集的部分需求）。

```json
{
  "requirements": {
    "people": 6,
    "budget_type": "total",
    "budget_fen": 15000,
    "dietary_constraints": [{"kind": "non_spicy", "people": 2}],
    "appetite": "normal",
    "preferred_tags": []
  },
  "missing_fields": [],
  "follow_up": null,
  "ready": true,
  "parse_source": "rule",
  "notes": []
}
```

- `ready=false` 时展示 `follow_up` 继续追问，**未齐时不要调 `/plans`**。
- `parse_source`：`rule`（内置规则兜底）/ `llm`（B 接入后）/ `demo_template`。
- 未给忌口人数时会追问 `有几位不吃辣？`，不会擅自按全部不辣处理。
- 金额只说数字没说口径时默认按总预算，并在 `notes` 里说明。

### 3.3 `POST /api/v1/plans`

输入：`{"store_code": "1400011", "requirements": {...}}`（requirements 与上同）。

返回 `data`：

```json
{
  "plans": [
    {
      "plan_id": "d5ba22f2c91f",
      "type": "cheapest",
      "title": "最省方案",
      "items": [
        {
          "code": "9900015602",
          "name": "大堡口福三件套",
          "quantity": 2,
          "unit_price_fen": 2290,
          "original_unit_price_fen": 4800,
          "line_total_fen": 4580,
          "servings": 1,
          "spicy_level": "mild",
          "image": "https://menu-img.mcd.cn/...",
          "nutrition": {"matched": false, "source": "mcd_mcp:list-nutrition-foods"}
        }
      ],
      "subtotal_fen": 17200,
      "total_fen": 10140,
      "budget_fen": 15000,
      "remaining_fen": 4860,
      "servings_total": 6,
      "non_spicy_servings": 2,
      "reasons": ["共 6 人份，其中不辣餐份 2 份", "..."],
      "checks": [
        {"name": "预算", "satisfied": true, "detail": "应付 101.4 元 / 预算 150.0 元"},
        {"name": "人数", "satisfied": true, "detail": "可满足 6 人份 / 共 6 人"},
        {"name": "忌口", "satisfied": true, "detail": "不辣餐份 2 / 需要 2"},
        {"name": "无需开卡", "satisfied": true, "detail": "..."}
      ]
    }
  ],
  "requirements": {},
  "total_budget_fen": 15000,
  "data_source": "live_mcp",
  "fetched_at": "2026-10-24 11:49:54",
  "degraded_reason": null,
  "unsatisfiable_reason": null,
  "suggestions": ["当前为接口演示样例（demo_sample）：...正式算法由 B 的 backend/skill 模块接入后替换"]
}
```

要点：

- **无解时 `plans=[]` 且 `unsatisfiable_reason` 非空**（HTTP 仍 200），页面展示原因与建议，不要硬凑三张卡片。
- `type` 取值：`cheapest` / `balanced` / `taste`。三种口径撞出同一组合时只返回一套并说明。
- `spicy_level`：`mild`（本地规则判定不辣）/ `spicy` / `unknown`（**未知，不得当成不辣展示**）。
- 菜单里 `discountType` 含「随单购」的商品标 `requires_membership=true`，其低价需同单购买麦金卡才成立，**不能直接按低价求和**。
- `suggestions` 里出现 `demo_sample` 说明当前走的是 A 的演示样例而非 B 的正式算法，**路演时不能说成算法已接入**。
- `plan_id` 由服务端保存并绑定门店与需求，结算按服务端方案重建金额。

## 四、A ↔ B 的模块契约（关键）

A 不实现 B 的算法，只负责**发现、调用、降级**。B 在以下位置创建文件即可自动接入，无需改动 A 的代码。

### 4.1 需求提取：`backend/llm.py`（B 维护）

```python
from backend.schemas import Requirements

async def extract_requirements(message: str, current: Requirements | None) -> dict:
    return {
        "requirements": Requirements(...),   # 合并 current 后的完整需求
        "missing_fields": [],                # 仍缺的字段：people / budget / non_spicy_people
        "follow_up": None,                   # 追问话术
        "parse_source": "llm",
        "notes": [],
    }
```

不存在或异常时，A 自动回退到内置规则解析（`parse_source=rule`）。
**禁止在该模块里直接调 MCP**——业务数据由 A 的 providers 统一供给。

### 4.2 方案生成：`backend/skill/__init__.py`（B 维护）

```python
from backend.schemas import MenuItemOut, NutritionOut, PlanOut, Requirements

def generate_plans(
    items: list[MenuItemOut],              # 该门店全部商品，含辣度/会员标记
    requirements: Requirements,            # 完整需求
    nutrition: dict[str, NutritionOut],    # 营养表，按商品名索引，可能为空
) -> tuple[list[PlanOut], str | None]:
    # 返回 (方案列表, 不可满足原因)；原因非空时列表应为空
    ...
```

- 同步或 `async` 均可，A 会自动兼容。
- 不需要返回 `plan_id` 时留空，A 负责生成与持久化。
- 约束必须满足：`total_fen <= requirements.total_budget_fen`、
  `servings_total >= requirements.people`、`non_spicy_servings >= requirements.non_spicy_people`。
- **不要自行读取 MCP 或另建菜单数据**（协作文档约定）。
- 不存在或异常时，A 回退到 `services/sample_planner.py` 的演示样例并在
  `suggestions` 标注 `demo_sample`。

### 4.3 参考实现

`backend/services/sample_planner.py` 是一份可运行的简化实现，
B 可以照着它理解数据结构与约束口径，但它是**要被替换的样例，不是正式算法**：
不做优惠叠加、不做营养优化、不使用开卡对比。

## 五、给 C 的前端对接要点

1. **金额只显示不计算**：`total_fen / 100` 格式化即可。
2. **三个标识必须可见**：`data_source`（真实/演示）、`degraded_reason`（降级原因）、订单 `is_demo`。
3. **`unknown` 辣度要透出**：建议文案「辣度未知，请按个人情况选择」，不要默认显示不辣。
4. **状态覆盖**：加载中 / 上游失败 / 无解（`unsatisfiable_reason`）/ 方案过期（409）。
5. **换门店后**：旧 `plan_id` 会返回 `E_PLAN_NOT_FOUND`，应引导重新生成方案。
6. 样例 JSON 在 `docs/api-examples/`，字段以这些真实响应为准。
